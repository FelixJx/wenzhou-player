# 数据抓取需求 v1 —— 让「AI 游客评审」变得好玩的最小数据集

日期：2026-10-24 ｜ 服务对象：PRD-v3 行程设计评审 ｜ 执行方：tools/crawl-lab 管线（沿用既有纪律）

**核心原则：数据不是越多越好，是"能制造戏剧时刻"的才要抓。** 每一条数据都应该能变成一句游客的狠话、一次扑空、一个惊喜。抓不到的宁空勿编（空=游戏不触发该事件；编错=口碑事故）。

## 三、数据格式（与 crawl-lab 既有纪律对齐）

### 3.1 POI 事实记录（每点一条，`tools/crawl-lab/results/poi-facts.json`）
```json
{
  "placeId": "xianqian",
  "name": "县前头小吃",
  "category": "food",
  "hours": { "mon": "07:00-20:00", "tue": "07:00-20:00" },
  "closedDays": [],
  "selloutBy": "14:00",
  "queueMin": { "peak": 25, "normal": 5 },
  "crowd": { "workday": { "morning": 2, "noon": 4, "afternoon": 3, "evening": 2 },
             "weekend": { "morning": 3, "noon": 5, "afternoon": 4, "evening": 3 } },
  "pricePerHead": 18,
  "signature": ["汤圆", "馄饨"],
  "tasteTags": ["甜", "软糯"],
  "bestTime": "07:00-09:00",
  "localTip": "本地人下午来不用排队",
  "sources": [{ "field": "hours", "platform": "大众点评", "url": "...", "at": "2026-10-24", "cacheAge": "fresh" }]
}
```
- **字段级溯源**：hours 可以是点评、bestTime 可以是笔记——来源跟到字段，不整条一个来源。
- **置信三级**：`verified`（官方/实地）> `platform`（点评/携程详情页）> `hearsay`（笔记/估计）。**判定引擎只认前两级；hearsay 只准进 LLM 评语素材。**

### 3.2 步行时间矩阵（`tools/crawl-lab/results/walk-matrix.tsv`）
列：`from, to, minutes, meters, source`。主干 10×10（center/wuma/mochi/xianqian/teastall/pier/lane1/lane2/xiechi/stage）；远郊三点只记"车程分钟"单值。来源：高德/百度步行路线规划 API 优先，实测次之。

### 3.3 现有产物衔接
- `public-facts.tsv` 已有 3 家餐厅（名称/地址/营业时段/仅开门时间/来源营业描述/来源平台/采集时间/缓存年龄/来源链接）→ **列兼容扩展**，新字段加列不换格式。
- 沿用红线：模糊"全天"不转 24h；缺失/冲突分列保存；评分保留平台标签不混填；缓存年龄照记。

## 四、抓多少才够（好玩验收标准）

**数量下限**：12 个市区地点 hours 全覆盖；主干步行矩阵 10×10；每点 ≥1 条 localTip/冷知识；售罄/排队 ≥4 家。合计约 **120–150 个字段值**，按现有管线一天可采完，人工校准半天。

**抓够了的游戏表现（缺一条就是数据还不够）**：
1. 随机排一条路线，至少 2 位游客在行前说出**基于真实数据**的疑虑；
2. 一局至少发生 1 次"扑空/赶上/末班船"级别的时段事件；
3. 结算评审里至少 1 个问题让玩家答不上来（冷知识驱动的提问）；
4. 5 位游客的评审**互相矛盾**（怕挤挤骂的恰好是买买买夸的——数据支撑不同视角）；
5. 玩家改一条路线（换一个点/挪一个时段），评审的分数和批评**随之改变**。
